## 1. Phase 1 전제 재정의 — "b 5 → 400 발굴" 폐기

- **구 전제(오류)**: OSM `man_made` 태그만으로는 b가 거의 없다(속초 실측 3 way) → 위성 분류로
  방파제를 "발굴"해 b를 5 → 400으로 늘린다.
- **실제**: 103차 파이프라인이 coastline "가는 육지 조각" 추론으로 b를 이미 **2,583타일 · 118성분**
  생성한다 — 양끝 바다 런 ≤ 10타일(50m) + 성분 ≥ 12타일 + 인프라(도로·건물) 성분 가드.
- **107차 실기 검증**: 오검출 **0건**(바다 비접촉 성분 0 · 백사장/도로변 b 없음) ·
  주요 방파제 전 성분 스폰에서 도보 도달 O · 도달 불가 12성분 101타일 = 전부 조도 갯바위·이안제
  (detached — 스펙 §3-2-4 의도된 불가).
- **재정의된 Phase 1 목표**: 발굴이 아니라 **위성 ↔ 추론 diff 검증 + 정밀화** —
  폭(현행은 런 ≤ 10타일 근사) · 끝단(두부) 형상 · 이안제 분리 여부 · 테트라포드 열 위치.
- **우선순위 격하**: Phase 1은 블로커가 아니다 — Phase 2(피복 분류)·오토타일 뒤로 미룬다.

## 2. §6 병합 — "래스터 b vs 추론 b" 규칙 신설

병합 단계에서 b 판정이 소스별로 어긋날 때의 처리를 고정한다.

| 케이스 | 처리 |
|---|---|
| OSM 태그 b (`man_made=breakwater\|pier\|groyne\|quay`) | **항상 유지** — 명시 데이터 최우선 |
| 래스터 b ∩ 추론 b (합의) | 확정 b — diff 리포트의 기준선 |
| 추론 b만 (래스터는 육지/기타) | **유지** — 추론이 실기 검증 통과(오검출 0). 단 래스터가 그 타일을 **바다**로 분류하면 자동 삭제하지 말고 검수 후보 목록에만 올린다 |
| 래스터 b만 (추론 없음) | 신규 후보 — 103차 가드(성분 ≥ 12타일 + 인프라 성분 + 바다 접촉) 통과 시만 채택, 나머지는 리포트만 |

- **patch.json은 병합 결과보다 항상 우선**한다 (103차 속초 재빌드에서 patch 보존 전례).
- 산출물: `raster_b_diff.json` — agree / raster_only / infer_only 타일 수 + 성분별 좌표 목록.
  사용자 육안 검수의 입력이 된다.
- 회귀 기준: 병합 후에도 "바다 비접촉 b 성분 0 · 주요 방파제 도보 도달 O"가 유지되어야 한다
  (107차 §5-b 검증 프로브 재실행).

## 3. §8-7 개정 — 낚시 판정 "교체" 폐기 → "현행 유지 + b/s 보너스"

- **실측 손익** (107차 §5-b): 현행 규칙(걷기 타일 + 인접 8방 바다) 발판 = **7,593타일** /
  §8-7 교체 규칙(b|s + 인접 바다) = **1,584타일** — **79% 상실**.
- b/s ⊂ 걷기 타일이므로 **교체가 새로 여는 발판은 0개** — 방파제 낚시는 현행 규칙으로 이미 된다.
- 상실분의 실체 = 속초항 내항 부두 안벽 (542,351) · **청초호 내안 전체** (448,458) —
  실제 감성돔·숭어 낚시터라 고증에도 역행.
- **개정**: 판정은 현행 유지(`OSM_TILEMAP_SPEC` §0.5-2). b/s는
  `isFishableStandTerrain`([RegionMap.ts:47](../packages/core/src/types/RegionMap.ts#L47) —
  §0.5-2가 예약해 둔 그대로)을 **스폰/입질 가중 보너스**로 소비한다.
- 보너스 배선(클라이언트/core)은 발주 범위 밖 — Claude Code 측 후속 작업.

## 4. Phase 3(DEM) 방침 — **경사는 차단이 아니라 태그** (2026-09-03 사용자 결정)

향후 **채집(해루질 포함)·광질** 시스템이 들어온다. 실제 지질/생태 재현이 아니라 **농사·건축
제작 재료 획득과 이벤트**를 위한 시스템이다(사용자: *"실제와 같은 구현을 통해 표현·활용하겠다는
취지는 아니야"*). 그래서 고도 데이터의 역할이 바뀐다.

- **원칙: 경사도로 통행을 막지 않는다.** 원 스펙 §5-2의 `slope > 35° → walkable=false 후보`는
  기본 비활성으로 둔다. 막아버리면 그 지형이 **채집·광질·이벤트 후보에서 통째로 빠진다**
  (사용자: *"접근 불가한 영역이 될거고, 이벤트나 다른 요소들에 활용할 것들도 한번에 배제"*).
  차단이 필요한 특정 지점만 `patch.json`에 수동 반영한다.
- **경사·고도는 "지형 태그"로 소비한다** — 자원 배치·스폰·이벤트의 **입력 신호**:
  급경사 해안 = 갯바위(해루질·따개비/홍합) · 암반 노출 = 광질 노드 · 완경사 초지 = 채집.
- **우선순위: B(해안 지형 변형) 최우선**, A(음영)·C(레벨/절벽)는 배제하지 않고 뒤로 둔다.
  단 **낚시 관련 확립이 먼저** — Phase 3 전체가 로드맵 후순위다(사용자 확인).
- ⚠ **A(음영)는 통행에 영향이 0이다** — 청크 베이크 틴트 1패스일 뿐 걷기 판정을 건드리지 않는다.
  "음영 = 접근 불가"가 아니다(개념 혼동 방지용 명시).
