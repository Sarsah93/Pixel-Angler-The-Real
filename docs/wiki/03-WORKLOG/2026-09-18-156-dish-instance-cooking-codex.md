## 1. 배경 — 왜 했나

사용자가 기획서와 함께 지시한 핵심 명제는 **「레시피 ≠ 요리」** 였다.

154차 불요리는 **레시피 1개 = 아이템 1개**다. 우럭을 넣든 광어를 넣든 결과는 늘 같은
`매운탕` 아이템이고, 이름도 회복치도 판매가도 동일했다. 어떤 생선을 잡아 왔는지가
결과물에 전혀 남지 않는다 — 낚시 게임에서 **조리는 어획의 종착지인데 어획이 사라진다.**

착수 범위도 사용자가 지정했다.

> "이번 작업에서 실제 구현은 매운탕 3종 → DishInstance → 상세보기 → 요리 도감까지만 먼저
> 완성하고, 정상 작동을 확인한 뒤 나머지 7개를 확장하는 방식이 가장 좋다."

그래서 이번 차수는 **기획서 Stage 1~6**(우럭·광어·감성돔 매운탕)까지다.
나머지 7개 레시피(Stage 7)·아이템 라이브러리(Stage 8)·밸런싱(Stage 9)은 사용자 확인 후.

## 2. 원인 — 무엇이 문제였나

기능 추가 차수지만, 구현 중 **실측으로 잡은 결함 3건**이 있다.

**① 발견 토스트가 내부 id를 그대로 화면에 뱉었다** (§8-9 위반).
실측 로그: `[도감] 새로운 아이템 발견 — inv_dish_stew_red_1 (N 키로 확인)`.
기전은 154차가 아니라 그 이전부터다 — `InventoryStore.addItem`은 **모든** 신규 아이템을
`DiscoveryStore.record('item', id)`로 기록하는데, 개체형 id(`inv_dish_*` · `inv_catch_*`)는
아이템 위키 카탈로그에 없어 `displayNameOf`가 **id를 그대로 반환**한다.
어획물은 `subCategory: '어획물'`이 카탈로그에서 제외돼 이름이 없을 뿐 토스트는 원래도 떴다.

**② 효과 지속 시간 문장이 영문 사전을 비껴갔다** (131차 함정의 변종).
효과 DB의 원문은 `30분 동안 허기 감소 속도 -8%`인데, 실제 표시 문장은 개체마다 다르다
(지방감 비례 — 감성돔 `32분` · 우럭 `29분` · 광어 `28분`). 사전은 **정확 일치**라 전부 미번역.

**③ 비린 향 라벨이 4단계인데 사전 등록 프로브가 3개였다.**
`fishinessLabel`의 밴드는 `[0.15, 0.35, 0.6]` 4구간인데 i18n이 `0.1 / 0.5 / 0.9`만 훑어
**`약함`(0.15~0.35) 한 칸이 통째로 빠졌다**(EN 실렌더에서 한국어 잔존으로 발견).

**설계 결정(⚖)**

- ⚖ **개체마다 새 아이템을 만들지 않는다.** 결과는 `InvItem.dishInstance`에 실려 저장되고,
  이름·회복치·판매가·효과는 전부 그 개체에서 나온다. 카탈로그·상점 목록은 불변.
- ⚖ **기전이 있는 효과는 포만감(허기 드레인 버프) 하나뿐**이다(기획서 §0.5).
  나머지 7종은 **표시 데이터**로만 둔다 — 실기전을 한 번에 8개 열면 생존 밸런스가 통째로 흔들린다.
- ⚖ **수식어는 최대 1개**(탄 → 일품 → 싱싱한 → 기름진). 두 개가 붙으면 이름이 길어지고
  무엇이 좋은 요리인지 읽히지 않는다.
- ⚖ **도감 기록은 (레시피 × 주재료) 1건**이다. 개체마다 등록하면 도감이 로그가 된다.
  비변형 레시피도 `kind: 'dish'`로 통일해 `discovery_<recipe>_generic` 1건을 갖는다.

## 4. 구조상 위치

`S4 손질·요리 → 불요리(154차) → 요리 개체화(156차)`.

건드린 층은 **계약 + 데이터 + 판정**이다.
154차 조리 엔진(`CookingSim`의 온도·익음·간·순서 시뮬)은 **한 줄도 고치지 않았다** —
`finishCook`이 낸 `DishData`를 입력으로 받아 `DishInstance`를 **덧붙이는** 층이다.
렌더는 상세보기·도감 두 곳만 추가됐고, 조리 패널(`CookingPanel`)은 무변경.

## 6. 잔여 — 이번에 안 한 것

- **Stage 7 — 나머지 7개 레시피 변형**(지리·생선구이·조림·오징어볶음·조개탕·전복죽·장어구이).
  착수 조건 = 사용자가 매운탕 3종 동작을 확인한 뒤. `VARIANT_RECIPES`에 id를 넣고
  어종 프로필을 넓히면 되는 구조로 이미 열려 있다.
- **Stage 8 — 아이템 라이브러리**(재료·완성 요리 열람). 도감 「요리」 탭이 선행 뼈대다.
- **Stage 9 — 밸런싱**: `TUNING.cook.{ingredientQuality, dishEffect, naming, pricing}`은
  **mockup 값**이다. 실플레이 조율 대기.
- 포만감 외 효과 7종의 실기전(§0.5 결정 — 표시만).
- 어종 조리 프로필은 우럭·광어·감성돔 3종이 실측 기준이고 나머지는 어종군 기본값 파생.

## 7. 위험·부작용

- **판매가가 이동한다.** 완성 요리는 이제 재료·품질·신선도로 값이 매겨져
  같은 레시피라도 ₩29,100~33,600으로 갈린다(154차는 고정). 요리 판매 수입 곡선이 위로 이동.
- **구세이브 호환은 유지**된다 — `dishInstance`가 없는 154차 요리는 기존 분기를 그대로 탄다
  (`getSellPrice`가 `item.dish && item.dishInstance`일 때만 새 경로).
- **도감 총계가 바뀐다**(요리 57칸 신설). 기존 도감 3탭 수치에는 영향 없음.
- 어종 프로필을 나중에 바꾸면 **이미 만들어 둔 요리 개체는 그대로다**(개체에 결과가 굳어 있다 — 의도).
